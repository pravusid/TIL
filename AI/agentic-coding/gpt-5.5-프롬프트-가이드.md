# GPT 5.5 프롬프트 가이드

## 주요 지침

### 1. “어떻게 해라”보다 “무엇이 성공인가”를 써라

GPT-5.5는 세부 절차를 강제하기보다, 목표 결과·성공 기준·제약·사용 가능한 근거·최종 답변 형태를 주는 방식이 적합합니다. 예를 들어 “A를 보고 B를 보고 C를 비교한 뒤…”처럼 순서를 과하게 고정하지 말고, “고객 이슈를 끝까지 해결하고, 최종 답변에는 completed_actions, customer_message, blockers를 포함하라”처럼 완료 상태를 정의하는 식입니다. ([OpenAI 개발자][1])

실무적으로는 이렇게 바꾸면 됩니다.

```text
나쁜 방향:
먼저 A를 확인하고, 그다음 B를 확인하고, C를 비교하고,
모든 예외를 검토한 뒤, 어떤 도구를 쓸지 결정하고...

좋은 방향:
사용자의 문제를 end-to-end로 해결한다.
성공 기준:
- 사용 가능한 정책/계정 데이터로 판단을 완료한다.
- 가능한 조치는 답변 전에 수행한다.
- 최종 답변에는 완료한 조치, 사용자에게 전달할 메시지, 남은 blocker를 포함한다.
- 근거가 부족하면 가장 작은 단위의 누락 정보만 질문한다.
```

### 2. `ALWAYS`, `NEVER`, `must`는 진짜 불변 조건에만 써라

문서에서는 절대 규칙을 남발하지 말라고 합니다. 안전 규칙, 필수 출력 필드, 절대 하면 안 되는 행동처럼 **진짜 invariant**에만 쓰고, 검색 여부·질문 여부·도구 사용 여부·반복 여부 같은 판단 영역은 “decision rule”로 표현하는 것이 낫습니다. ([OpenAI 개발자][1])

예:

```text
별로 좋지 않음:
항상 검색해라. 절대 추측하지 마라. 항상 5개 이상의 출처를 확인해라.

더 좋음:
핵심 질문에 답하기에 충분한 근거가 있으면 답변한다.
필수 사실, 날짜, 소유자, 파라미터, 출처가 빠졌을 때만 추가 검색한다.
```

### 3. 중단 조건을 명시하라

GPT-5.5에서는 “언제 멈출지”를 프롬프트에 넣는 것이 중요합니다. 예를 들어 “정확성과 필수 citation을 해치지 않는 범위에서 가장 적은 tool loop로 해결하라”, “핵심 질문에 답할 수 있으면 추가 검색하지 말고 답하라” 같은 stopping rule을 두는 방식입니다. ([OpenAI 개발자][1])

특히 에이전트/검색형 워크플로우에서는 다음 문구가 유용합니다.

```text
각 검색 결과 후 다음을 판단한다:
“지금 가진 근거와 citation으로 사용자의 핵심 요청에 답할 수 있는가?”
그렇다면 추가 검색하지 말고 답변한다.
```

### 4. retrieval budget을 둬라

근거 기반 답변에서는 “검색 예산”을 정의하라고 합니다. 일반 Q&A는 짧고 구분력 있는 키워드로 한 번 넓게 검색하고, 상위 결과만으로 충분하면 바로 답변합니다. 추가 검색은 핵심 질문이 해결되지 않았거나, 필수 사실·날짜·ID·소스가 빠졌거나, 사용자가 포괄적 비교/목록을 요구했거나, 특정 문서/URL/이메일/코드 아티팩트를 반드시 읽어야 할 때로 제한합니다. ([OpenAI 개발자][1])

좋은 패턴:

```text
일반 Q&A는 1회 broad search로 시작한다.
상위 결과가 핵심 요청을 충분히 뒷받침하면 답변한다.
다음 경우에만 추가 검색한다:
- 핵심 질문에 답하지 못함
- 필수 사실/날짜/ID/출처가 없음
- 사용자가 exhaustive comparison/list를 요구함
- 특정 문서/URL/이메일/코드를 반드시 읽어야 함
```

### 5. personality와 collaboration style을 짧게 분리하라

GPT-5.5의 기본 스타일은 효율적이고 직접적이며 task-oriented입니다. 고객-facing assistant라면 “어떤 말투인가”를 정하는 personality와 “어떻게 일하는가”를 정하는 collaboration style을 짧게 정의하라고 합니다. 단, personality는 사용자 경험을 조정하는 용도이지, 목표·성공 기준·도구 규칙·중단 조건을 대체하면 안 됩니다. ([OpenAI 개발자][1])

예:

```text
# Personality
친절하지만 장황하지 않다. 사용자를 유능한 실무자로 가정한다.

# Collaboration style
요청이 충분히 명확하면 질문보다 진행을 우선한다.
누락 정보가 결과를 크게 바꾸거나 리스크를 만들 때만 좁은 질문을 한다.
불확실성은 명확히 표시하고, 가능한 경우 합리적 가정을 둔다.
```

### 6. 긴 작업·도구 작업은 preamble을 사용하라

스트리밍 UI에서는 모델이 추론하거나 도구 호출을 준비하는 동안 첫 토큰이 늦게 보일 수 있습니다. 그래서 긴 작업, multi-step 작업, tool-heavy workflow에서는 시작 시 짧은 user-visible update를 보내도록 프롬프트에 지시하는 것이 권장됩니다. ([OpenAI 개발자][1])

예:

```text
멀티스텝 작업 또는 도구 호출이 필요한 경우,
도구 호출 전에 요청을 확인하고 첫 단계를 설명하는 짧은 업데이트를 보낸다.
1~2문장으로 제한한다.
```

### 7. 출력 형식은 `text.verbosity`와 output contract로 제어하라

GPT-5.5는 출력 구조와 형식 제어가 잘 되므로, `text.verbosity`, 예상 출력 구조, 대상 독자, 길이 제한을 명시하라고 합니다. 기본 `text.verbosity`는 `medium`이고, 더 짧은 답변을 원하면 `low`를 사용하라고 설명합니다. 또한 문서·기술 설명·일반 대화에서는 과한 헤더와 bullet을 피하고, 구조는 이해를 돕는 경우에만 쓰는 것이 권장됩니다. ([OpenAI 개발자][1])

예:

```text
대상 독자: 시니어 엔지니어
길이: 400단어 이하
구조: 결론 → 근거 → caveat
불필요한 bullet과 header는 피한다.
```

### 8. 근거 기반/창작 작업은 사실과 창작을 분리하라

슬라이드, 런칭 카피, 고객 요약, talk track 같은 생성 작업에서는 “출처 기반 사실”과 “창의적 표현”을 구분하라고 합니다. 제품 기능, 고객명, 지표, 로드맵, 날짜, 경쟁사 주장 같은 구체적 claim은 제공되거나 검색된 근거에 기반해야 하며, 근거가 부족하면 placeholder나 명시적 가정을 사용해야 합니다. ([OpenAI 개발자][1])

예:

```text
구체적인 제품 기능, 고객명, 수치, 일정, 경쟁 비교는 제공된 근거만 사용한다.
근거가 없으면 단정하지 말고 [확인 필요] 또는 명시적 가정으로 표시한다.
표현은 자연스럽게 다듬되, 새로운 사실 claim은 만들지 않는다.
```

### 9. 검증 가능한 작업은 self-check를 명시하라

코딩 에이전트라면 변경 후 관련 unit test, type check, lint, build, smoke test 중 가장 적절한 검증을 실행하도록 지시하는 것이 좋습니다. 실행할 수 없으면 그 이유와 차선의 검증 방법을 설명하게 하라고 합니다. 시각 자료는 렌더링 후 레이아웃, clipping, spacing, 누락, 시각적 일관성을 검사하도록 지시합니다. ([OpenAI 개발자][1])

예:

```text
변경 후 가능한 가장 관련성 높은 검증을 실행한다:
- 변경된 동작의 targeted unit test
- type check 또는 lint
- 영향받은 package build
- full validation이 비싸면 minimal smoke test
검증을 실행할 수 없으면 이유와 차선 검증 방법을 설명한다.
```

### 10. tool-heavy Responses workflow에서는 `phase`를 보존하라

긴 작업이나 도구 호출이 많은 Responses workflow에서는 assistant item의 `phase` 값을 사용해 중간 업데이트와 최종 답변을 구분할 수 있습니다. `previous_response_id`를 쓰면 상태가 보존되지만, assistant output item을 직접 replay하는 구조라면 기존 `phase` 값을 그대로 보존해야 합니다. 중간 업데이트는 `commentary`, 최종 답변은 `final_answer`로 다루라고 설명합니다. ([OpenAI 개발자][1])

## 추천 프롬프트 구조

문서가 제안하는 복잡한 프롬프트의 기본 구조는 다음과 같습니다. 핵심은 **짧게 시작하고, 실제 실패 모드를 고치기 위해 필요한 블록만 추가**하는 것입니다. ([OpenAI 개발자][1])

```text
Role:
[모델의 역할, 맥락, job을 1~2문장으로 정의]

# Personality
[톤, 태도, 협업 스타일]

# Goal
[사용자에게 보이는 최종 결과]

# Success criteria
[최종 답변 전에 반드시 충족되어야 하는 조건]

# Constraints
[정책, 안전, 비즈니스, 근거, side-effect 제한]

# Output
[섹션, 길이, 톤, 형식]

# Stop rules
[언제 재시도/중단/질문/대체/거절할지]
```

정리하면, GPT-5.5용 프롬프트는 **짧고, 결과 중심이며, 검증 가능하고, 멈출 줄 아는 계약서**처럼 쓰는 것이 좋습니다. 과거처럼 “생각 순서”를 길게 통제하기보다, **성공 상태·제약·근거 기준·출력 계약·중단 조건**을 명확히 두는 쪽이 핵심입니다.
